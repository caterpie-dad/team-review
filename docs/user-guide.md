# 대시보드 사용 안내

[운영 설치](../README.md) · [문서 목록](index.md)

## 주요 기능

- 고유 팀원 ID, 복수 GitHub 계정/Confluence ID 연결, 중복 귀속 방지, 비활성화
- 프로젝트 카드, 날짜 선택, 참여자 클릭 선택, 가중치 슬라이더와 균등 분배
- 프로젝트 가중치 합 100 검증, 평가 복제, 완료·확정 평가의 구성 편집, 초안 삭제
- Confluence 루트 하위 페이지 순회, 기간 내 버전 변경분과 수정자 귀속
- GitHub repo/org 범위 수집, 조직 소유 저장소 목록 저장, 기본 브랜치 커밋 diff 분석
- 평가 진행률, 단일 평가 실행 잠금, 취소, 실패 시 재시도, 서버 재시작 복구
- 품질 35% / 난이도 25% / 검증 25% / 협업 전달력 15% 기준의 LLM 평가
- 구조화 응답, 근거 ID 허용 목록과 원문 인용 검증, 신뢰도·한계·누락 경고 표시
- 개인 종합 및 프로젝트별 점수, 근거 원문/URL/해시, 미귀속 산출물 확인
- 점수·평가 의견 조정, 원점수 복원, 자동 재집계, 충돌 방지와 감사 이력
- 최종 확정/해제, 사후 편집 이력, JSON/CSV 내보내기, CSV 수식 주입 방지
- 비밀번호 인증, 세션 만료, CSRF 방어, 로그인 시도 제한, CSP, 비밀키 비노출

## 프로젝트 근거 링크 추가

프로젝트별 GitHub·Confluence 입력란에 URL을 하나씩 넣고 **＋ 추가** 또는 Enter를 누릅니다. 추가한 링크는 입력란 아래 목록에 표시되며, 각 항목의 **✕**로 제거할 수 있습니다. 기존 평가를 편집할 때도 저장된 링크가 모두 표시됩니다. 서비스별 최대 30개까지 등록할 수 있으며 입력만 하고 추가하지 않은 링크가 있으면 저장 전에 안내합니다.

등록한 GitHub 저장소·조직과 Confluence 루트들을 모두 수집 대상으로 사용합니다. 조직에서 해석한 저장소나 여러 루트의 하위 페이지가 겹치면 중복 근거는 한 번만 처리합니다. 설정된 수집 한도에 도달하면 경고로 표시합니다. 수집 범위와 전체 근거는 결과 화면에서 확인할 수 있습니다.

평가 진행 화면과 대시보드는 진행률·상태 문구를 주기적으로 갱신합니다. 진행 중에는 화면 전체를 다시 만들지 않아 스크롤·포커스·펼친 경고가 유지되며, 완료되면 결과 화면으로 전환합니다.

## 완료된 평가 편집과 재분석

**초안 저장**은 입력 중인 구성을 보관합니다. 평가/프로젝트 이름, 날짜, 참여자, 근거 링크가 비어 있거나 프로젝트 가중치 합계가 100이 아니어도 저장·재편집할 수 있습니다. 저장한 초안에는 보완할 항목을 표시하며, **평가 시작** 시 필수 설정·가중치·근거 범위를 검증합니다. 오류에는 프로젝트 순서와 항목명을 한국어로 표시합니다. 완료된 평가의 사후 편집에는 완성된 설정이 필요합니다.

평가 목록의 **편집**, 결과 화면의 **평가 편집**에서 프로젝트 추가·제거, 참여 팀원 추가·제거/프로젝트 이동, 이름·기간·근거 링크·프로젝트 가중치를 수정합니다. **최신 팀원 정보 반영**을 선택하면 수정된 계정·이름·연차도 평가에 적용됩니다. 편집 중 **팀원 등록**으로 새 사람을 등록할 수 있습니다.

- 프로젝트 이름/가중치, 기준 이름/비율, CL 계수 변경: 호환되는 판정과 수동 조정을 보존하고 즉시 재집계합니다.
- 참여자 추가, 계정 매핑·기간·근거 링크·평가 내용/점수 구간 변경: 영향을 받은 항목만 **재분석 필요**로 표시합니다. 오래된 점수를 새 조건의 결과로 사용하지 않습니다.
- **변경 항목 재분석**: 필요한 항목만 분석하고 나머지 결과와 수동 보정은 유지합니다.
- **전체 다시 분석**: 현재 서비스 설정으로 전부 다시 수집·분석합니다. 이전 실행은 이력에 남으며 유효한 수동 점수·의견은 유지합니다.
- **평가 의견 편집**: 기여 요약과 판단의 한계를 편집합니다. LLM 원문은 별도 보존합니다.
- 완료/확정 평가 수정에는 사유를 남깁니다. 확정된 평가도 편집할 수 있고 저장하면 검토 상태로 돌아갑니다. 재분석이 남은 결과는 확정할 수 없습니다.
- 진행 중인 평가는 취소/완료 후 편집합니다. 시작된 작업의 근거 범위가 도중에 바뀌지 않도록 합니다.

**평가 기준** 탭에서 네 기준의 이름·내용·비율, 점수 구간 및 CL 계수를 편집할 수 있습니다. 기본 기준은 새 평가에 적용되며, 기존 평가는 **평가 편집 → 현재 기본 기준 불러오기 → 저장**으로 명시적으로 적용합니다. 평가별 기준도 같은 화면에서 직접 편집할 수 있습니다. 기준 비율의 합은 100입니다.

## 대시보드에서 서비스 설정

**서비스 연결** 탭에서 GitHub/Confluence의 웹·API URL, Bearer/Basic 인증, 사용자 및 토큰, LLM의 API URL·모델·API Key·JSON 모드를 설정합니다. 각 서비스에 **연결 테스트**와 **연결 설정 저장** 버튼이 있습니다.

연결 테스트는 저장 전 입력값을 사용합니다. GitHub/Confluence는 인증 사용자 응답을, LLM은 지정 모델의 짧은 응답을 확인합니다. LLM 테스트는 소량의 API 사용량이 발생할 수 있습니다. 성공해도 모든 저장소/페이지의 개별 접근 권한까지 보장하지는 않습니다. API 오류 본문이나 인증키는 화면·이력에 반환하지 않습니다.

토큰 입력란은 항상 비어 있으며 공란으로 저장하면 기존 키를 유지합니다. 변경할 때 새 키를 입력하고, 삭제할 때 **저장된 인증키 삭제**를 선택합니다. 화면에서 저장한 값은 기본 TOML/환경 변수보다 우선하며 DB 옆의 `review-settings.json`(DB 파일 이름에 따라 달라짐)에 권한 0600으로 원자적으로 저장됩니다. Docker의 `/data` 영속 볼륨에 남으므로 재시작해도 유지됩니다. 설정 백업 시 이 파일도 함께 보관해야 합니다. 평가 실행 중에는 공통 설정 저장을 막고 연결 테스트는 가능합니다.

## 평가 방식과 해석

각 차원은 0~100점 또는 판정 보류입니다. 프로젝트의 개인 점수는 네 차원의 기준 가중합입니다. 보정 전 종합점수는 **판정 가능한 참여 프로젝트의 점수 × 프로젝트 가중치 / 해당 가중치 합**이며, 최종 종합점수는 여기에 **CL 계수**를 한 번 곱합니다. 참여하지 않은 프로젝트는 분모에서 제외하고, 판정하지 못한 참여 비중은 충족률로 드러냅니다. 판정 보류가 있으면 잠정 결과입니다. 평가자가 조정하면 같은 공식으로 즉시 재계산하며 LLM 원점수는 남습니다. 충족률은 점수를 산출할 수 있는 비중이며, 점수의 정확성이나 충분한 관찰을 보장하는 수치가 아닙니다.

평가 시작 시 팀원·기준을 보존합니다. 구성 변경은 이전 버전을 이력에 남기고 반영합니다. 재시도는 성공한 결과를 유지하고 남은 항목을 처리합니다. 전체 다시 분석은 모든 항목을 새로 분석하되 유효한 평가자 보정은 유지합니다. 최종 확정은 평가자의 검토 단계입니다. 자료 부족은 낮은 기여의 증거로 취급하지 않습니다.

수집 경계와 현재 한계:

- GitHub는 **기본 브랜치에 포함된 커밋**을 UTC committer 날짜로 제한합니다. 미병합 브랜치, PR 리뷰, 이슈, 첨부파일은 수집하지 않습니다. 병합 커밋의 중복 diff는 제외합니다.
- GitHub 변경 파일은 커밋당 100개까지 읽습니다. 바이너리, 생략된 diff, 생성물, 수집 상한은 제외 또는 경고로 표시합니다. 조직의 fork/archived repo는 제외합니다.
- Confluence는 수집 시점에 루트 아래에 있는 페이지를 대상으로 과거 버전 변경분을 읽습니다. 삭제/이동되어 현재 루트 밖에 있는 페이지, 첨부파일, 접근 불가 버전은 복원하지 않습니다. 버전 불일치나 API 접근 실패를 숨기지 않고 실행을 실패시킵니다.
- 코드 주 저자/문서 버전 수정자를 매핑합니다. 공동 저자 커밋은 주 저자에게만 귀속하고 경고합니다. 매핑 모호성은 자동 추측하지 않습니다.
- 두 프로젝트에 같은 근거가 포함되면 경고합니다. 평가자는 프로젝트 구분과 가중치를 검토해야 합니다.
- 모델은 웹 검색/도구 실행 권한이 없으며 제공된 근거만 받습니다. ID·인용 검증은 근거 연결의 정확성을 확인하지만, 모델의 의미 해석이 항상 옳음을 보장하지 않습니다.
- 큰 자료는 배치별로 평가하고 동일 가중으로 평균합니다. 배치 경계의 영향을 한계로 표시합니다. 한 배치에서라도 해당 차원을 판정하지 못하면 그 차원은 보류합니다.

## LLM 분석 비용 줄이기

기본 `analysis.github_strategy = "adaptive"`는 같은 작성자의 **부모 SHA로 연결된 연속 커밋**을 4~32개씩 묶습니다. 해당 구간의 마지막 파일 blob을 읽고 Git 해시를 검증한 뒤 모든 diff를 역으로 적용하여 이전 상태까지 확인합니다. LLM에는 커밋 이력, 순변경, 최종 파일 문맥, 중간에 추가/삭제되었다가 사라진 코드·테스트를 중복 제거하여 보냅니다. 기존 코드의 문맥을 해당 팀원의 기여로 간주하지 않도록 구분합니다. 최종 파일은 현재 HEAD가 아니라 **평가 기간 안의 해당 구간 커밋에 고정**됩니다.

작성자 변경 지점은 별개 구간입니다. 병합·공동 저자·미매핑·불완전한 diff·이름 변경·해시 불일치 등은 원본 diff 방식을 유지합니다. 최종 파일이 너무 크거나 통합 입력의 절감률이 20% 미만이면 적용하지 않습니다. 저장한 원본 커밋 근거는 삭제하지 않으며 통합 근거 화면에서 원본을 열 수 있습니다. 중간 변경의 세부 순서는 통합 입력에서 생략되므로 원본 이력 검토가 가능합니다.

동일한 근거·범위·팀원 매핑·평가 기준·프롬프트·모델·서비스 인증 설정의 검증된 LLM 결과는 SQLite `judgment_cache`에 보존합니다. 재사용할 때 근거 인용을 다시 검사하고, 평가자의 수동 보정은 캐시에 넣지 않습니다. 캐시는 기본 최대 2,000개 배치이며 재시작 후에도 유지됩니다. **전체 다시 분석**은 캐시 조회를 건너뛰고 새 판정으로 캐시를 갱신합니다. 문서 판정에도 동일 캐시를 적용하지만 Confluence 수집은 기존 버전별 작성자 diff를 유지합니다.

결과의 **분석 효율**에 근거 본문 문자 수, 통합 구간, LLM 요청, 캐시 사용, API가 제공한 실제 토큰 수를 표시합니다. 문자 수와 토큰 수를 구분하며 수량은 평가 점수에 사용하지 않습니다. 원본 수집·작성자 추적 API 요청은 계속 수행하므로 이 개선은 주로 LLM 입력과 호출 비용을 줄입니다.

설정 파일의 `[analysis]`에서 `github_strategy = "diff"`로 기존 분석 방식을 사용할 수 있고, `cache_enabled = false`로 캐시를 끌 수 있습니다. `max_snapshot_bytes`(기본 128,000), `max_snapshot_files`(구간당 20), `min_savings_ratio`(0.2)로 통합 한도를 조정합니다.

## 연차별 기대 수준 보정

팀원은 연차와 기준 연도를 등록합니다. GitHub/Confluence ID는 하나씩 **추가** 버튼 또는 Enter로 넣으며 바로 아래 목록에서 확인·삭제합니다. Git 이메일은 등록하거나 귀속에 사용하지 않습니다.

| 평가 연도 기준 연차 | CL | 기본 종합점수 계수 | 산출물 점수 80점일 때 |
| --- | --- | ---: | ---: |
| 1–8년차 | CL2 | 1.00 | 80 |
| 9–16년차 | CL3 | 0.90 | 72 |
| 17년차 이상 | CL4 | 0.80 | 64 |

연차는 `등록 연차 + 평가 연도 − 기준 연도`로 계산합니다. 예를 들어 2026년 8년차는 2027년 평가에서 9년차/CL3입니다. 계수는 평가 기준 화면 또는 TOML의 `[evaluation]`에서 `level_weights = { CL2 = 1.0, CL3 = 0.9, CL4 = 0.8 }`로 변경할 수 있습니다. `0 < CL4 < CL3 < CL2 ≤ 1`을 검증해 동점 산출물의 CL 역전을 방지하고 100점 상한 절단으로 생기는 동점을 피합니다.

산출물 기준의 LLM 원점수와 개인별 프로젝트 점수는 보존하고 **종합점수에만 한 번 적용**합니다. LLM에 연차를 전달하여 이중 보정하지 않습니다. 결과와 CSV에는 보정 전 점수, 평가 연도 기준 연차, CL, 적용 계수가 함께 표시됩니다. 점수를 조정하면 이 공식을 다시 적용합니다.

평가 시작 시 연차 정보와 계수를 고정하므로 이후 팀원 정보나 서버 설정을 바꿔도 과거 평가 결과는 달라지지 않습니다. 보정 도입 전 평가는 기존 점수를 유지하며 화면에 이를 표시합니다. 기존 팀원의 연차는 추측하지 않으므로 새 평가 시작 전에 입력해야 합니다. 과거 데이터의 Git 이메일 필드는 마이그레이션에서 제거하고 기존 점수는 유지합니다.
